## 준비물 체크

- [ ] 이 저장소가 GitHub에 push 되어 있다 (`git remote -v` 로 확인)
- [ ] GitHub 저장소 페이지 상단의 **Actions** 탭 위치를 안다
- [ ] 로컬에서 편집 → `git add` → `git commit` → `git push` 흐름이 익숙하다

작업 규칙: **매 미션마다 커밋 + push** 하고, Actions 탭에서 결과를 눈으로 확인하세요.

## 미션 1 · 수동 실행되는 워크플로우 만들기

**목표:** 버튼으로 실행되는 가장 단순한 워크플로우 1개.

**할 일**
1. 파일 생성: `.github/workflows/hello.yml`
2. 아래 요구사항을 만족하도록 작성:
   - 워크플로우 이름(`name`)은 `My First Workflow`
   - 트리거는 **수동 실행만** (`workflow_dispatch`)
   - job 1개 (id는 `hello`), `ubuntu-latest` 에서 실행
   - step 1개: `echo "첫 번째 워크플로우 실행됨"` 출력
3. 커밋 & push
4. GitHub → **Actions** 탭 → 왼쪽에서 `My First Workflow` 선택 → **Run workflow** 버튼 클릭 → main 선택 → 실행
5. 실행 항목을 열어 `hello` job의 step 로그에 문구가 찍혔는지 확인

**확인 포인트**
- [ ] Actions 탭 왼쪽 목록에 `My First Workflow` 가 보인다
- [ ] `Run workflow` 버튼이 있다 (이게 `workflow_dispatch` 의 효과)
- [ ] 실행 로그에 `첫 번째 워크플로우 실행됨` 이 있다

<details>
<summary>힌트</summary>

```yaml
name: My First Workflow

on:
  workflow_dispatch:

jobs:
  hello:
    runs-on: ubuntu-latest
    steps:
      - name: 인사 출력
        run: echo "첫 번째 워크플로우 실행됨"
```
`run:` 만 있는 step은 러너의 셸에서 그 명령을 그대로 실행합니다.
</details>

## 미션 2 · push 될 때 자동 실행되게 하기

**목표:** 커밋을 push 하면 워크플로우가 저절로 돈다.

**할 일**
1. `hello.yml` 의 `on:` 에 `push` 트리거 추가
2. 단, **이 폴더와 이 워크플로우 파일이 바뀔 때만** 실행되도록 `paths` 필터 추가
   - `02-first-workflow/**`
   - `.github/workflows/hello.yml`
3. 커밋 & push
4. Actions 탭에서 이번엔 **버튼을 안 눌렀는데도** 실행이 새로 생겼는지 확인

**확인 포인트**
- [ ] push 직후 Actions 탭에 새 실행이 자동으로 생겼다
- [ ] 실행 화면 상단 트리거가 `push` 로 표시된다
- [ ] (실험) 루트 `README.md` 만 살짝 고쳐 push 하면 → 이 워크플로우는 **실행되지 않는다** (paths 필터 때문)

<details>
<summary>힌트</summary>

```yaml
on:
  workflow_dispatch:
  push:
    paths:
      - "02-first-workflow/**"
      - ".github/workflows/hello.yml"
```
트리거는 여러 개를 나열할 수 있습니다. `paths` 는 `push` 안에 들여씁니다.
</details>

## 미션 3 · 코드 체크아웃 + 실행 정보 출력

**목표:** 재사용 액션(`uses`)과 컨텍스트 표현식(`${{ }}`) 사용.

**할 일**
1. `hello` job의 **첫 step** 으로 `actions/checkout@v4` 추가
2. 그 다음 step에서 아래를 출력 (한 step에서 여러 줄 → `run: |`)
   - `실행한 사람: ${{ github.actor }}`
   - `트리거 이벤트: ${{ github.event_name }}`
   - `브랜치: ${{ github.ref_name }}`
3. 마지막 step에서 `ls -al` 로 체크아웃된 파일 목록 출력
4. 커밋 & push → 로그 확인

**확인 포인트**
- [ ] `ls -al` 결과에 `README.md`, `01-what-is-cicd` 등 저장소 파일이 보인다
  (checkout 을 빼면 파일이 없다 — 일부러 빼서 차이를 봐도 좋음)
- [ ] `트리거 이벤트` 가 `push` 또는 `workflow_dispatch` 로 상황에 맞게 찍힌다

<details>
<summary>힌트</summary>

```yaml
    steps:
      - name: 코드 체크아웃
        uses: actions/checkout@v4

      - name: 실행 정보 출력
        run: |
          echo "실행한 사람: ${{ github.actor }}"
          echo "트리거 이벤트: ${{ github.event_name }}"
          echo "브랜치: ${{ github.ref_name }}"

      - name: 파일 목록
        run: ls -al
```
</details>

## 미션 4 · step 실패 동작 관찰하기

**목표:** step 하나가 실패하면 이후 step이 어떻게 되는지 직접 본다.

**할 일**
1. `ls -al` step **앞에** 일부러 실패하는 step 추가: `run: exit 1`
2. 커밋 & push → 실행 결과 확인
3. 관찰한 내용을 아래 README 의 "배운 점"에 메모
4. **실패 step 제거** 하고 다시 커밋 & push (원상복구)

**확인 포인트**
- [ ] `exit 1` step에 빨간 X 표시가 뜬다
- [ ] 그 **뒤의 `ls -al` step은 실행되지 않고** 회색(skipped)으로 남는다
- [ ] job 전체가 실패(빨간색)로 끝난다
- [ ] (선택) 실패해도 다음 step을 실행시키려면 `continue-on-error: true` 를 검색해보기

## 미션 5 · 두 번째 job을 순서대로 실행하기

**목표:** `needs` 로 job 간 실행 순서를 만든다.

**할 일**
1. `done` 이라는 job을 새로 추가 (`ubuntu-latest`)
2. `done` job은 `hello` job이 **성공한 뒤에만** 실행되도록 `needs: hello` 설정
3. `done` job의 step: `echo "hello job이 끝나서 done job 실행됨"`
4. 커밋 & push → Actions 실행 화면의 **job 그래프**가 `hello → done` 순서로 이어지는지 확인

**확인 포인트**
- [ ] 실행 상세 화면에서 두 job이 화살표로 연결돼 보인다
- [ ] `hello` 가 도는 동안 `done` 은 대기(pending) 상태다
- [ ] (실험) `needs: hello` 를 지우면 두 job이 **동시에** 시작된다

<details>
<summary>힌트</summary>

```yaml
jobs:
  hello:
    runs-on: ubuntu-latest
    steps:
      # ... 미션 1~3 내용 ...

  done:
    runs-on: ubuntu-latest
    needs: hello
    steps:
      - run: echo "hello job이 끝나서 done job 실행됨"
```
job은 기본적으로 병렬입니다. `needs` 가 유일한 순서 제어 수단입니다.
</details>
