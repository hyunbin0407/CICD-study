# 9회차 실습 · 실제 배포 자동화 — Part 1

> 개념 설명은 [`README.md`](./README.md). 이 문서는 **터미널에 그대로 붙여넣어 진행**하는 실습입니다.
> Part 1의 목표: 배포 대상 앱 준비 → Docker Hub에 수동 push → Render에 서비스 수동 생성 →

> ⚠️ Render 계정 생성과 서비스 생성은 **브라우저에서 직접** 해야 하는 부분입니다 (`gh` CLI로는

## 미션 2 · Docker 이미지 빌드 + Docker Hub push (수동)

**배우는 것:** 아직 CI 없이 로컬에서 직접 빌드/검증/push — Part 2에서 이 과정을 CI로 옮긴다

### ① 로컬 빌드 + 컨테이너 실행 검증

```bash
cd ~/Workspace/CICD-study
docker build --platform linux/amd64 -t gusqls0718/cicd-study-deploy:latest 09-deploy/app

docker run -d -p 3000:3000 --name deploy-test gusqls0718/cicd-study-deploy:latest
sleep 1
curl -s http://localhost:3000/ | python3 -m json.tool
docker stop deploy-test && docker rm deploy-test
```

> 📌 **`--platform linux/amd64`가 왜 필요한가** (5회차와 동일한 함정): Apple Silicon(M시리즈)
> Mac에서 `docker build`는 기본적으로 호스트 아키텍처인 **arm64**로 이미지를 만든다. 그런데 Render의
> 무료 인스턴스는 **linux/amd64**에서만 동작한다 — arm64 이미지를 Render에 넣으려 하면 "invalid
> platform" 에러로 거부당한다. `--platform linux/amd64`를 명시하면 Docker Desktop이 QEMU로 amd64
> 이미지를 크로스 빌드해준다 (로컬에서 `docker run`으로 실행할 땐 에뮬레이션이라 약간 느릴 수 있다).

**확인 포인트**

- [ ] 컨테이너로 띄운 서버도 로컬 `npm start`와 동일한 응답 (에뮬레이션이라 응답이 조금 느릴 수 있음)

### ② Docker Hub에 push

## 미션 3 · Render에 "이미지 기반 서비스" 생성 (브라우저)

**배우는 것:** GitHub 연동 없이 Docker Hub 이미지만으로 서비스를 띄우는 방법

### ① Render 가입

1. https://render.com 접속 → Sign Up (GitHub 계정으로 로그인해도 되고, 이메일로 가입해도 됩니다 — 카드 등록 불필요)

### ② 새 Web Service 생성 — "Deploy an existing image"

1. Dashboard에서 **New +** → **Web Service**
2. 소스 선택 화면에서 GitHub 리포지토리 연결 대신 **"Deploy an existing image from a registry"** 선택
3. Image URL에 `docker.io/gusqls0718/cicd-study-deploy:latest` 입력
4. Name: `cicd-study-deploy` (원하는 이름으로)
5. Instance Type: **Free** 선택
6. **Create Web Service** 클릭 → 첫 배포가 시작됨 (몇 분 소요)

### ③ 배포 완료 확인

Render가 서비스에 부여한 URL(`https://<서비스이름>.onrender.com` 형태)을 복사해서 확인합니다.

```bash
RENDER_URL="여기에_방금_복사한_URL_붙여넣기"

curl -s "$RENDER_URL/" | python3 -m json.tool
curl -s "$RENDER_URL/format?amount=99999" | python3 -m json.tool
```

**확인 포인트**
- [ ] `/` 응답이 로컬에서 봤던 것과 동일한 JSON 구조로 옴
- [ ] Render 대시보드의 서비스 상태가 "Live"

<details><summary>힌트: 첫 응답이 느리거나 502가 뜬다면</summary>

무료 인스턴스는 처음 배포 직후 컨테이너가 완전히 뜰 때까지 시간이 좀 걸릴 수 있습니다.
Render 대시보드의 "Logs" 탭에서 `listening on ...` 로그가 찍혔는지 확인하고, 10~20초 후 다시
`curl`해보세요.
</details>

## 미션 4 · Deploy Hook을 GitHub Secret으로 저장

**배우는 것:** Deploy Hook URL을 비밀로 다루는 이유, `gh secret set`으로 안전하게 저장하기

### ① Render에서 Deploy Hook URL 복사

1. 방금 만든 서비스 페이지 → **Settings** 탭
2. **Deploy Hook** 항목에서 URL 복사 (`https://api.render.com/deploy/srv-...?key=...` 형태)

> ⚠️ 이 URL은 **채팅에 붙여넣지 마세요** — 이 URL을 아는 사람은 누구나 이 서비스를 재배포시킬 수
> 있습니다. 아래 `gh secret set` 명령은 값을 화면에 노출하지 않고 안전하게 입력받습니다.

### ② GitHub Secret으로 저장

```bash
cd ~/Workspace/CICD-study
gh secret set RENDER_DEPLOY_HOOK
```

프롬프트가 뜨면 복사해둔 Deploy Hook URL을 붙여넣고 Enter (터미널에 값이 그대로 보일 수 있는
환경도 있으니, 명령 실행 후 스크롤을 정리하거나 터미널을 지워도 좋습니다).

### ③ 저장됐는지 확인 (값이 아니라 존재 여부만)

```bash
gh secret list
```

**확인 포인트**
- [ ] `gh secret list` 목록에 `RENDER_DEPLOY_HOOK`이 보임 (값 자체는 당연히 안 보임, 그게 정상)

# Part 2 · CI에 배포 자동화 추가

> Part 1까지는 전부 수동(로컬 빌드, 수동 push, Render 수동 배포)이었습니다. Part 2에서는 이 과정을
> 하나의 워크플로우로 묶어서, `main`에 push 한 번이면 test부터 실제 재배포까지 전부 자동으로
> 돌아가게 만듭니다.

## 미션 1 · `test` job만 있는 워크플로우 먼저 만들기

**배우는 것:** `paths` 필터로 이 워크플로우가 `09-deploy/` 변경에만 반응하게 하기

### ① 파일 작성

```bash
cd ~/Workspace/CICD-study
mkdir -p .github/workflows
cat > .github/workflows/09-deploy.yml <<'EOF'
name: 09 - Deploy

on:
  push:
    branches:
      - main
    paths:
      - "09-deploy/**"
      - ".github/workflows/09-deploy.yml"

jobs:
  test:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: 09-deploy/app
    steps:
      - name: 코드 체크아웃
        uses: actions/checkout@v4

      - name: Node.js 설치
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
          cache-dependency-path: 09-deploy/app/package-lock.json

      - name: 의존성 설치
        run: npm ci

      - name: 테스트 실행
        run: npm test
EOF
```

> 📌 `paths: ["09-deploy/**"]`가 없으면, 이 리포지토리의 다른 회차 폴더(예: `08-advanced/`)만
> 고쳐도 이 워크플로우가 매번 같이 실행된다 — Docker 빌드+push+Render 재배포까지 전부 딸려온다.
> Part 2는 2회차에서 배운 `paths` 필터를 실전에 써먹는 자리이기도 하다.
>
> ⚠️ **워크플로우 파일 자신의 경로(`.github/workflows/09-deploy.yml`)도 `paths`에 같이 넣어야
> 한다.** 이 파일은 `09-deploy/` 폴더 밖에 있다 — `"09-deploy/**"`만 넣으면 지금 이 미션처럼
> 워크플로우 파일 자체를 새로 만들거나 고치는 push는 조건에 안 맞아서 **아예 실행이 안 되는**
> 역설적인 상황이 된다. 아래 커맨드는 이미 두 경로를 모두 넣어뒀다.

### ② 커밋 & push

Part 1 미션1에서 `npm install`로 생긴 `package-lock.json`이 아직 커밋 안 돼있을 수 있습니다 — CI의
`npm ci`가 이 파일을 필수로 요구하니 워크플로우 파일과 같이 커밋합니다.

```bash
git add .github/workflows/09-deploy.yml 09-deploy/app/package-lock.json
git commit -m "9회차 Part2 미션1: test job만 있는 09-deploy 워크플로우"
git push origin main
```

### ③ 실행 확인

```bash
sleep 8
RUN_ID="$(gh run list --workflow 09-deploy.yml -L1 --json databaseId -q '.[0].databaseId')"
gh run watch "$RUN_ID"
```

**확인 포인트**
- [ ] `test` job이 `success`

## 미션 2 · `docker-push` job 추가 (amd64 빌드 + 태그 2개)

**배우는 것:** CI 안에서도 `--platform linux/amd64`가 필요한 이유, `github.sha`로 커밋별 태그 남기기

### ① 파일 수정 — `docker-push` job 추가

```bash
cat > .github/workflows/09-deploy.yml <<'EOF'
name: 09 - Deploy

on:
  push:
    branches:
      - main
    paths:
      - "09-deploy/**"
      - ".github/workflows/09-deploy.yml"

jobs:
  test:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: 09-deploy/app
    steps:
      - name: 코드 체크아웃
        uses: actions/checkout@v4

      - name: Node.js 설치
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
          cache-dependency-path: 09-deploy/app/package-lock.json

      - name: 의존성 설치
        run: npm ci

      - name: 테스트 실행
        run: npm test

  docker-push:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - name: 코드 체크아웃
        uses: actions/checkout@v4

      - name: Docker Buildx 설정
        uses: docker/setup-buildx-action@v3

      - name: Docker Hub 로그인
        uses: docker/login-action@v3
        with:
          username: ${{ vars.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: 빌드 + push
        uses: docker/build-push-action@v6
        with:
          context: 09-deploy/app
          platforms: linux/amd64
          push: true
          tags: |
            docker.io/gusqls0718/cicd-study-deploy:latest
            docker.io/gusqls0718/cicd-study-deploy:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
EOF

git add .github/workflows/09-deploy.yml
git commit -m "9회차 Part2 미션2: docker-push job 추가 (linux/amd64)"
git push origin main
```

> 📌 CI 러너(`ubuntu-latest`)는 원래 amd64라서 Render와 아키텍처가 같다. 그런데도
> `platforms: linux/amd64`를 명시하는 이유는, 이걸 안 쓰면 `docker/build-push-action`이 기본으로
> "러너와 같은 아키텍처 하나"를 만드는데 이게 우연히 맞는 것과 **의도적으로 명시하는 것**은 다르다 —
> 나중에 워크플로우를 다른 러너(예: `macos-latest`)로 옮기거나 멀티 아키텍처로 확장할 때 사고를
> 막아준다.

### ② 실행 확인 — job 2개 다 성공하는지

```bash

RUN_ID="$(gh run list --workflow 09-deploy.yml -L1 --json databaseId -q '.[0].databaseId')"
gh run watch "$RUN_ID"
gh run view "$RUN_ID" --json jobs -q '.jobs[] | {name, conclusion}'
```

**확인 포인트**
- [ ] `test`, `docker-push` 둘 다 `success`

## 미션 3 · `deploy` job 추가 — Render Deploy Hook 호출

**배우는 것:** `curl -f`로 실패를 job 실패로 전파시키기, secret이 로그에 안 찍히는 것 확인

### ① 파일 수정 — `deploy` job 추가

```bash
cat > .github/workflows/09-deploy.yml <<'EOF'
name: 09 - Deploy

on:
  push:
    branches:
      - main
    paths:
      - "09-deploy/**"
      - ".github/workflows/09-deploy.yml"

jobs:
  test:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: 09-deploy/app
    steps:
      - name: 코드 체크아웃
        uses: actions/checkout@v4

      - name: Node.js 설치
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
          cache-dependency-path: 09-deploy/app/package-lock.json

      - name: 의존성 설치
        run: npm ci

      - name: 테스트 실행
        run: npm test

  docker-push:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - name: 코드 체크아웃
        uses: actions/checkout@v4

      - name: Docker Buildx 설정
        uses: docker/setup-buildx-action@v3

      - name: Docker Hub 로그인
        uses: docker/login-action@v3
        with:
          username: ${{ vars.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: 빌드 + push
        uses: docker/build-push-action@v6
        with:
          context: 09-deploy/app
          platforms: linux/amd64
          push: true
          tags: |
            docker.io/gusqls0718/cicd-study-deploy:latest
            docker.io/gusqls0718/cicd-study-deploy:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  deploy:
    needs: docker-push
    runs-on: ubuntu-latest
    steps:
      - name: Render Deploy Hook 호출
        run: |
          curl -sf -X POST "${{ secrets.RENDER_DEPLOY_HOOK }}"
EOF

git add .github/workflows/09-deploy.yml
git commit -m "9회차 Part2 미션3: deploy job 추가 - Render Deploy Hook 호출"
git push origin main
```

> 📌 `curl -sf`의 `-f`(`--fail`)가 핵심이다. 이게 없으면 Render가 400/500을 응답해도 `curl`은
> 종료 코드 0으로 끝나서 **job이 `success`로 잘못 보고된다.** `-f`를 붙이면 HTTP 에러 응답일 때
> `curl`이 0이 아닌 코드로 종료해서 step이, 그리고 job이 진짜로 `failure`가 된다.

### ② 실행 확인

```bash
sleep 15
RUN_ID="$(gh run list --workflow 09-deploy.yml -L1 --json databaseId -q '.[0].databaseId')"
gh run watch "$RUN_ID"
gh run view "$RUN_ID" --json jobs -q '.jobs[] | {name, conclusion}'
```

**확인 포인트**
- [ ] `test`, `docker-push`, `deploy` 셋 다 `success`

### ③ 로그에 Deploy Hook URL이 노출 안 되는지 확인

```bash
gh run view "$RUN_ID" --log | grep -i "curl" | head -5
```

**확인 포인트**
- [ ] 로그에 찍힌 `curl` 명령에 실제 URL 대신 `***`로 마스킹되어 있음 (GitHub가 secret 값을 자동으로
      가려주는 것)
