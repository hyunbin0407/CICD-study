이번 회차는 "브랜치별로 다르게 동작"이 주제라 `develop` 브랜치가 실제로 있어야 한다.

```bash

```

**확인 포인트**
- [ ] `git branch -a` 에 `remotes/origin/develop` 이 보임
- [ ] 현재 브랜치는 다시 `main`

## 미션 1 · `branches` 필터로 main/develop만 트리거

**배우는 것:** `on.push.branches`, 필터 밖 브랜치는 워크플로우 자체가 안 생긴다는 것

### ① 파일 작성

```bash
mkdir -p .github/workflows
cat > .github/workflows/06-triggers.yml <<'EOF'
name: 06 - Triggers

on:
  push:
    branches:
      - main
      - develop

defaults:
  run:
    working-directory: 03-auto-test/app

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: 코드 체크아웃
        uses: actions/checkout@v4

      - name: Node.js 설치
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
          cache-dependency-path: 03-auto-test/app/package-lock.json

      - name: 의존성 설치
        run: npm ci

      - name: 테스트 실행
        run: npm test
EOF
```

### ② 커밋 & push (main)

```bash
git add .github/workflows/06-triggers.yml
git commit -m "6회차 미션1: branches 필터로 main/develop만 트리거"
git push origin main
```

### ③ main에서 실행되는지 확인

```bash
sleep 5
RUN_ID="$(gh run list --workflow 06-triggers.yml -L1 --json databaseId -q '.[0].databaseId')"
gh run watch "$RUN_ID"
```

### ④ feature 브랜치 push는 트리거가 안 되는지 확인

```bash
git checkout -b feature/mission1-test
echo "// 6회차 미션1: 트리거 테스트용" >> 03-auto-test/app/src/money.js
git add 03-auto-test/app/src/money.js
git commit -m "6회차 미션1: feature 브랜치 트리거 테스트"
git push -u origin feature/mission1-test

sleep 5
gh run list --workflow 06-triggers.yml -b feature/mission1-test
```

**확인 포인트**
- [ ] main push는 `test` job이 `success`
- [ ] `gh run list ... -b feature/mission1-test` 결과가 **빈 목록** (run 자체가 안 생김 — 실패도 skip도 아님)

<details><summary>힌트: run이 있는데 skipped로 나온다면</summary>

`branches` 필터가 걸리면 목록 자체에 안 나와야 정상이다. 뭔가 나온다면 워크플로우 파일에 오타가
있거나(`branches` 밖에 있거나), 이전 커밋의 run이 섞여 보이는 것일 수 있다 — `-b` 옵션 값(브랜치명)을
다시 확인.
</details>

### ⑤ 정리 — feature 브랜치 삭제

```bash
git checkout main
git branch -D feature/mission1-test
git push origin --delete feature/mission1-test
```

## 미션 2 · `if` 조건으로 브랜치별 다른 step 실행

**배우는 것:** job/step 레벨 `if:`, `github.ref` vs `github.ref_name`, "실행되지만 안 도는 step"

### ① 파일 작성 (덮어쓰기) — `deploy-simulate` job 추가

```bash
cat > .github/workflows/06-triggers.yml <<'EOF'
name: 06 - Triggers

on:
  push:
    branches:
      - main
      - develop

defaults:
  run:
    working-directory: 03-auto-test/app

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: 코드 체크아웃
        uses: actions/checkout@v4

      - name: Node.js 설치
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
          cache-dependency-path: 03-auto-test/app/package-lock.json

      - name: 의존성 설치
        run: npm ci

      - name: 테스트 실행
        run: npm test

  deploy-simulate:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - name: prod 배포 (main push)
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        run: |
          echo "🚀 prod 배포! (ref=${{ github.ref }})"

      - name: staging 배포 (develop push)
        if: github.event_name == 'push' && github.ref == 'refs/heads/develop'
        run: |
          echo "🧪 staging 배포! (ref=${{ github.ref }})"
EOF
```

### ② main에 커밋 & push

```bash
git add .github/workflows/06-triggers.yml
git commit -m "6회차 미션2: if 조건으로 브랜치별 배포 시뮬레이션"
git push origin main
```

### ③ main 실행 결과 확인

```bash
sleep 5
RUN_ID="$(gh run list --workflow 06-triggers.yml -L1 --json databaseId -q '.[0].databaseId')"
gh run watch "$RUN_ID"
gh run view "$RUN_ID" --json jobs -q '.jobs[] | select(.name=="deploy-simulate") | .steps[] | {name, conclusion}'
```

**확인 포인트 (main)**
- [ ] `prod 배포` step이 `success`
- [ ] `staging 배포` step이 `skipped` (실패가 아니라 조건이 안 맞아서 건너뜀)

### ④ develop에도 반영해서 확인

```bash
git checkout develop
git merge main --ff-only
git push origin develop
git checkout main

sleep 5
RUN_ID="$(gh run list --workflow 06-triggers.yml -b develop -L1 --json databaseId -q '.[0].databaseId')"
gh run watch "$RUN_ID"
gh run view "$RUN_ID" --json jobs -q '.jobs[] | select(.name=="deploy-simulate") | .steps[] | {name, conclusion}'
```

**확인 포인트 (develop)**
- [ ] `staging 배포` step이 `success`
- [ ] `prod 배포` step이 `skipped`

같은 워크플로우 파일 하나가 **어느 브랜치에서 실행되느냐에 따라 다르게 행동**한다는 게 이 미션의 핵심.

## 미션 3 · 태그 push 트리거

**배우는 것:** `on.push.tags`, `startsWith()` 함수, 태그 push의 `ref` 형태

### ① 파일 작성 (덮어쓰기) — `tags` 추가 + prod 조건에 태그 포함

```bash
cat > .github/workflows/06-triggers.yml <<'EOF'
name: 06 - Triggers

on:
  push:
    branches:
      - main
      - develop
    tags:
      - "v*"

defaults:
  run:
    working-directory: 03-auto-test/app

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: 코드 체크아웃
        uses: actions/checkout@v4

      - name: Node.js 설치
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
          cache-dependency-path: 03-auto-test/app/package-lock.json

      - name: 의존성 설치
        run: npm ci

      - name: 테스트 실행
        run: npm test

  deploy-simulate:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - name: prod 배포 (main push 또는 태그 push)
        if: github.event_name == 'push' && (github.ref == 'refs/heads/main' || startsWith(github.ref, 'refs/tags/v'))
        run: |
          echo "🚀 prod 배포! (ref=${{ github.ref }})"

      - name: staging 배포 (develop push)
        if: github.event_name == 'push' && github.ref == 'refs/heads/develop'
        run: |
          echo "🧪 staging 배포! (ref=${{ github.ref }})"
EOF
```

### ② 커밋 & push (main)

```bash
git add .github/workflows/06-triggers.yml
git commit -m "6회차 미션3: 태그 push 트리거 추가"
git push origin main
```

이 push 자체는 그냥 main push라 미션2와 동일하게 prod만 성공할 것이다 — 확인은 생략하고 바로 태그로.

### ③ 태그 push해서 확인

```bash
git tag v0.1.0
git push origin v0.1.0

sleep 5
RUN_ID="$(gh run list --workflow 06-triggers.yml -L1 --json databaseId -q '.[0].databaseId')"
gh run view "$RUN_ID" --json headBranch,event,displayTitle
gh run watch "$RUN_ID"
gh run view "$RUN_ID" --json jobs -q '.jobs[] | select(.name=="deploy-simulate") | .steps[] | {name, conclusion}'
```

**확인 포인트**
- [ ] `headBranch`가 `v0.1.0` (태그 이름), `event`가 `push`
- [ ] `prod 배포` step이 `success` (로그에 `ref=refs/tags/v0.1.0` 찍힘)
- [ ] `staging 배포` step은 `skipped`

<details><summary>힌트: 태그 push인데 워크플로우가 아예 안 걸린다면</summary>

`git push origin v0.1.0` 대신 `git push origin main --tags` 처럼 브랜치와 같이 보냈는지, 태그
이름이 `v` 로 시작하는지(`tags: ["v*"]`) 확인. `git tag` 만 실행하고 `git push origin <태그명>` 을
빼먹으면 로컬에만 태그가 생기고 원격엔 아무 일도 안 일어난다.
</details>


- [ ] `release/1.0` push가 glob 패턴에 매치되어 워크플로우가 정상적으로 트리거됨
- [ ] `test` job `success`
- [ ] `deploy-simulate` job은 (PR이 아니므로) `success` 로 실행되지만, 그 **안의 3개 step은 전부
      `skipped`** — `ref`가 `refs/heads/release/1.0`라 어떤 조건에도 안 맞기 때문
- [ ] 이 결과를 미션5의 "job 자체가 skipped" 였던 것과 비교 — job 레벨 `if` vs step 레벨 `if`의 차이
